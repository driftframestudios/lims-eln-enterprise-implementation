# Enterprise Implementation repository re-entry

## Contract

- **What:** A repository-local method for recovering settled, current, open,
  and next implementation state.
- **When:** Work resumes after a handoff, branch or pull request changes, or
  source, release, living orientation, configured evidence, and external
  coordinates appear to disagree.
- **Boundaries:** Runnable source and tests define current behavior. Signed
  release evidence defines the accepted implementation baseline. Configured
  receipts observe their named environment. Repository edits and accountable
  acceptance stay with their named owners.
- **Result:** One authoritative source path, one live collaboration surface,
  the material difference among records, and one bounded next move.

## Rules

### Rule: Current source and accepted release answer different questions

Read the working branch for current behavior. Read the signed tag, promotion
observation, and retained release identities for what was accepted. Read each
configured receipt for what its exact environment demonstrated.

### Rule: The nearest carriers come before broad history

Read the root README, release role, Machine Node, First Receipt, Coordination
Horizon, public-inspection manifest, and relevant runbook before searching the
complete history. Follow the exact Issue, pull request, or workflow only when
live coordination affects the move.

### Rule: Evidence paths keep their posture

Distinguish local synthetic verification, configured-environment observation,
selected-future simulation, qualified use, accountable acceptance, and
production authorization.

### Rule: External coordinates retain their owners

Program and Governance contracts, Simulation closure, Comparative admission,
and implementation observations remain separately identified. This repository
can consume or bind them without becoming their source authority.

### Rule: Existing work remains intact

Identify unrelated worktree changes and neighboring worktree branches before
editing. Surface overlap instead of absorbing another collaboration's work.

### Rule: Stale status language becomes visible

When a living carrier describes a completed route as waiting, name the
difference and reconcile that carrier through its owning validator. Historical
Issues and immutable release evidence retain their original record.

## Operating sequence

1. Run `git status --short --branch`; inspect local, remote, and tag history.
2. Read `README.md`, `release/repository-role.json`, `machine-node.json`,
   `first-receipt.json`, `COORDINATION-HORIZON.json`, and the public-inspection
   manifest.
3. Identify the relevant contract, runnable source, migration, fixture,
   receipt, runbook, and tests.
4. Resolve the signed release subject and any later `develop` carrier.
5. Inspect the live Issue, pull request, and hosted check only where current
   status or authority changes the route.
6. State settled, current, open, and next terrain; identify any stale carrier.
7. Choose one source path, one receiver, and one stopping event.

## Completion

Re-entry completes when a collaborator can name current implementation
behavior, the accepted release, each material configured observation, the
difference among those states, and the next bounded move without reconstructing
the entire repository history.
